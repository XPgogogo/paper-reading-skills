# 长文档分层阅读报告

把一份几万字、结构松散、大量重复表述的方案文档，转成「顶部速览 + 可折叠详情 + 自绘架构图」的单文件 HTML。

## 何时用 / 何时不用

**用**：技术建设方案、项目建议书、可行性研究报告、白皮书、招投标文件、政策文件、评审材料——特征是**章节层级深、模板化表述多、验收指标散落在表格里、读者需要快速抓重点**。

**不用**：
- 学术论文 → 用「论文阅读」技能（有自己的四模式与笔记格式）
- 只要格式转换（docx→pdf）→ 直接转，不做报告
- 用户只要一句话摘要 → 直接答，别建 HTML

## 关键前置：先确认 4 个分叉再动手

这类任务**看起来清晰实则模糊**，直接做容易白干。必须先问（每问带选项 + 推荐理由）：

1. **组织主线**：总览框架+分层展开（推荐）／验收指标导向／忠实按原文结构
2. **详略层次**：速览+可展开详情（推荐）／详实完整版／极简速览
3. **是否加个人视角**：结合读者自身研究方向做切入点提示／纯客观梳理
4. **是否列原文问题**：单独成节（推荐）／不列／正文标注

> 若用户已说"直接做"，跳过提问，但交付时必须列出所采用的假设。

## 工作流

### 第 1 步：全文提取（不要只靠 MCP 读取工具）

**坑**：本地 Office MCP 的 `doc_get_outline` 在文档**未使用 Word Heading 样式**时返回空；`doc_resolve_document_structure` 每段只有 10~200 字预览，**拿不到全文**。方案文档经常只用自定义样式（pStyle 为数字如 `4`/`5`/`6`/`7`）靠字号区分层级，此时大纲工具全部失效。

**解法**：用 Python 标准库直接解析 `word/document.xml`，**保留 pStyle 编号**（后续靠它还原层级）：

```python
import zipfile, xml.etree.ElementTree as ET
W = "{http://schemas.openxmlformats.org/wordprocessingml/2006/main}"
root = ET.fromstring(zipfile.ZipFile(path).read("word/document.xml"))
body = root.find(W+"body")
# 遍历 body 直接子元素：W+p 取段落文本+pStyle，W+tbl 逐行逐格取表格
```

输出到临时 `.md`，段落前缀标 `[pStyle]`，表格用 `<<<TABLE START>>>` 包裹、单元格用 ` | ` 分隔。**然后用 Read 工具通读全文**——不要只读开头就动手。

> 用你系统上的任意 Python 3 解释器即可，zipfile/ET 都是标准库，无需额外装包。

### 第 2 步：核对数字口径（这一步最能产出价值）

方案文档的验收指标常与正文对不上。**必须逐项回原文点数**，别信作者写的数字：

- 验收表要求的数量 vs 正文实际列举的数量（分别数「概述段列举」和「设计方案逐条展开」两个口径，两者常不一致）
- 查找**整段复制残留**：不同子系统的「概述」段落是否逐字相同、是否出现了不属于本领域的术语（典型症状：生命科学章节里写着"地球科学""遥感影像"）
- 查找**内容与标题不符**：模块名说 A，正文写的是 B
- 查找**重复条目**：同一工具/模块描述出现两遍
- 查找**量化门槛缺失**：验收指标是否全是"支持/具备 XX 功能"，而正文却写"大幅提升""打破瓶颈"——论述与验收口径的落差是评审风险点
- 图表编号是否跳号（说明是章节摘录）
- 术语错别字：介观/界观、表型/表形、Illumina/lumina、扩散模型/扩散扩散模型

用脚本统计比肉眼可靠：

```python
from collections import Counter
Counter(tools)          # 找重复
set(A) - set(B)         # 找两个口径的差集
re.findall(r"图 (5-\d+)", t)   # 图表编号连续性
```

### 第 2.5 步：关键词点数验证法（回答"有没有 X"类问题的硬手段）

当用户问**"有没有规划""进度如何""谁负责""做到什么程度"**时，**不要凭阅读印象回答**。印象会说"应该有吧"，点数会说"0 次命中"。这两者的差距就是报告的价值。

**做法**：把抽象问题拆成可扫描的关键词组，对全文逐词统计命中次数：

```python
groups = {
 "进度/时间":   ["进度","时间节点","里程碑","工期","排期","第一阶段","建设周期","实施计划","时间表","阶段划分","2024","2025","2026","2027","2028"],
 "分工/人员":   ["分工","承担单位","责任单位","课题组","负责人","人员配置","团队","牵头","参与单位","人力"],
 "预算/经费":   ["预算","经费","投入","万元","资金","成本核算"],
 "现状/基线":   ["现状","目前已有","现有基础","已具备","已完成","已建成","前期基础","基线"],
 "风险/验证":   ["风险","保障措施","应急预案","质量控制","测试方案","验证方案","评审"],
 "量化门槛":    ["加速比","并行效率","精度达到","误差小于","规模达到","吞吐量"],
}
```

**两个必须做的防误判动作**：

1. **命中不等于有效命中**。实测案例：扫"基线"命中 2 次，逐条看原文发现都是 CPA 模型的**「基线潜变量」技术术语**，与"项目起点基线"无关；扫"风险"命中 2 次，一处是"盲目试错风险"（效果描述）、一处是 Trimmomatic 的"质量控制"（软件功能）。**必须把命中行打出来人工判定**，不能只报数字。

2. **反向统计语气词**。扫 `拟 / 将 / 有望 / 计划` 的频次——实测"拟"出现 **165 次**、"将" 49 次，各模块设计方案几乎每段都以「拟提供」「拟采用」开头。**这一项比正向统计更能说明文档处于意向态还是执行态**，是判断"规划成熟度"的关键证据。

同理可做**动作性质分类统计**，用于回答"到底要做什么"：

| 语义类 | 关键词 | 实测频次 |
|---|---|---|
| 优化/加速（跑快） | 优化 加速 提升 重构 改进 | 261 |
| 集成/适配（搬上国产） | 适配 集成 封装 引入 整合 部署 迁移 | 162 |
| 研发/突破（自己造） | 发展 突破 开发 提出 自主研发 | 60（"自主研发"仅 **1** 次）|
| 意向态语气 | 拟 将 有望 计划 | 217 |

**结论的说服力来自对比**：261 vs 162 vs 60 直接说明这是**工程适配项目而非算法创新项目**；"自主研发"仅 1 次说明原创成分极低。这类点数结果应做成条形图放进报告（见第 5 步）。

### 第 3 步：写 HTML —— 必须分段写，一次写完会被截断

**坑**：`Write` 工具单次写入超过约 39KB 会 JSON 解析失败（`Unexpected non-whitespace character after JSON`）。一份完整报告通常 100~130KB。

**解法**：
1. 第一次 `Write` 只写**骨架**：完整 `<head>`（含全部 CSS）+ `<header>` + `<nav>` + 空的 `<div class="wrap"><!--SECTIONS--></div>` + `<footer>` + `<script>`
2. 之后每节用 `Edit`，`old_string="<!--SECTIONS-->"`，`new_string="本节内容\n<!--SECTIONS-->"`——**保留占位符**，下一节继续替换
3. 最后一节把占位符一并删掉

这样每次调用只写 15~25KB，稳定不截断。

### 第 4 步：报告结构（验证有效的 9 节式）

```
① 三分钟速览    KPI 数字卡 + 「N 句话读懂」有序列表 + 指向②的指引条 + 阅读建议
② 三问三答 ★    要做什么 / 有没有规划 / 怎么做 —— 用第 2.5 步的点数结果作答，每问配证据表
③ 全局架构图    自绘 SVG，一图看清层级骨架 + 关键技术锚点
④⑤ 各领域分系统  手风琴卡片，每个子系统可展开：定位/设计原则/模块卡网格/验收表/注意框
⑥ 验收指标总表   N 张表汇总成 1 张，硬数字高亮，口径问题就地标注
⑦ 共性技术套路   归纳模板化结构（读者掌握后可跳过 60% 正文）+ 领域对比表
⑧ 与读者的关联   简短提示，不展开分析，判断权交还读者
⑨ 原文待核问题   按 高/中/低 三级分组，每条含：严重度标签 + 原文行号 + 引文 + 修改建议
```

**② 三问三答是读者最想要的一节，务必放在速览之后、架构图之前。** 初版把它省了，读者追问"讲清楚要做什么、有没有规划、怎么做"才补——说明**读者要的是判断，不只是梳理**。三问的答题范式：

- **每问开头一个「一句话答案」高亮框**，先给结论
- **紧跟证据表**（点数结果 / 原文精确措辞 / 行号），让结论可核查
- **Q2 必须两面都写**：既指出实施规划缺失（0 命中的硬证据），也要说明技术规划扎实的部分（设计原则、两大支柱、四段式结构），避免把文档说得一无是处
- **Q3 给出"最大捷径"**：明确告诉读者精读哪 1~2 个模块即可推断其余，可跳过多少正文
- **末尾一张「三问收束表」**：问题 / 答案 / 依据三栏，一屏看完

**②③ 之间避免重复内嵌同一张 SVG**。若 Q3 需要引用架构图或流程图，用**锚点跳转提示条**（`<a href="#pattern">`）+ 3~5 行要点速记，比复制一份 SVG 更好：文件更小、不会出现两份图不同步。

**交互要点**：手风琴用纯 CSS `max-height` 过渡 + 一段 8 行 JS 绑定点击；配「全部展开/收起」按钮。避免 `<details>`（样式难统一）。

**插入新章节后的收尾三件事**（漏一个就会留下不一致）：
1. 导航栏 `<nav>` 整体替换
2. 章节编号用正则按出现顺序统一重排（见第 6 步代码）
3. header 的阅读时长提示、footer 的统计数字按实测回填

### 第 5 步：SVG 图必须用脚本生成坐标

**坑**：手写多列布局的 x 坐标极易重叠。实测案例——3 个子系统框写成 `x=42/192/342, width=186`，区间 42~228、192~378、342~528 **两两重叠**；5 列布局最后一个框 `x=970+178=1148` **超出 viewBox 宽 1140**。肉眼在代码里看不出来，渲染后才发现糊成一团。

**解法**：用 Python 按公式算，不要手填数字：

```python
LM, RM = 40, 1100          # 左右边距
BW = RM - LM               # 可用总宽
gap = 16                   # 列间距
cw = (BW - gap*(n-1)) / n  # 列宽
centers = [LM + i*(cw+gap) + cw/2 for i in range(n)]
```

把「列标题 + 模块行列表」写成数据结构，用函数循环生成 `<rect>`/`<text>`，y 坐标累加计算，函数返回 `bottom` 供下一段接着排。

**生成后必须跑几何自检**（这一步不能省）：

```python
rects = [tuple(map(float, m.groups())) for m in
         re.finditer(r'<rect x="([-\d.]+)" y="([-\d.]+)" width="([\d.]+)" height="([\d.]+)"', svg)]
# 1) 越界：x+w > viewBox宽 或 y+h > viewBox高
# 2) 同层重叠：两两判 not (a右<=b左 or b右<=a左 or a下<=b上 or b下<=a上)
#    注意排除"子矩形嵌套在容器内"的正常包含关系——只比较尺寸相近的同层元素
# 3) 文本溢出：按 CJK≈1.0em / ASCII≈0.55em / 空格≈0.30em / 大写≈0.68em 估宽，
#    配合 text-anchor(start/middle/end) 算出 x0~x1，检查是否超出所属容器
```

### 第 6 步：整体校验后交付

```python
# 标签配对计数（div/section/table/svg/span/b/p/li...）
# div 深度模拟：遍历 <div 和 </div>，终值必须为 0、过程最小值必须 >= 0
# 逐 section 检查内部 div 平衡差
# 导航锚点 set(href) - set(id) 必须为空
# 残留占位符 count("<!--SECTIONS-->") 必须为 0
# 乱码 count("\ufffd") 必须为 0
```

**替换 SVG 块时特别注意边界（高频坑，已栽过两次）**：
用 `h.index('图注关键词')` 再往后找 `</div>` 定位结尾时，**第一个 `</div>` 命中的是图注 `.cap` 自己的闭合标签，不是外层 `.fig` 容器的**——因为 `.cap` 就写成 `<div class="cap">...</div>` 单行。结果替换后旧的 `.fig` 闭合标签残留，div 计数多出 1 个 `</div>`，深度变 -1。

正确做法：从图注位置**连续吃掉两个 `</div>`**（`.cap` 的 + `.fig` 的），或直接用正则锚定完整结构：

```python
s = h.index('<div class="fig"')                      # 起点用容器开头，别用图注
e = h.index('</div>', h.index('图 A · ', s))          # 第一个 = .cap 的闭合
e = h.index('</div>', e) + len('</div>')              # 第二个 = .fig 的闭合 ← 别漏这行
h = h[:s] + new_svg + h[e:]
```

改完**必须重跑 div 深度模拟**（终值 0、最小值 ≥0），并逐 section 查平衡差，才能定位到是哪一节出的问题。

### 追加章节时的编号与锚点维护

用户看完初版常会追问，需要插入新章节。此时：

- **导航栏 `<nav>` 要整体替换**，不要逐个改
- **章节编号 `<span class="no">NN</span>` 用正则按出现顺序统一重排**，不要靠标题文字匹配（标题后常带 `<span class="tag">` 等标签，精确字符串匹配会失败）：

```python
order = list(re.finditer(r'<div class="sec-h"><span class="no">(\d+)</span><h2>', h))
for i in range(len(order)-1, -1, -1):        # 从后往前替换，避免偏移失效
    m = order[i]; want = "%02d" % (i+1)
    if m.group(1) != want:
        s, e = m.span(1); h = h[:s] + want + h[e:]
```

- **页脚统计数字（几节/几图/几表）要在最后用代码实测回填**，不要手写——`h.count("<svg")` 会把 16×16 的箭头图标也计入，注意区分或如实描述。

### 横向条形图的标签越界坑

左侧标签若用 `text-anchor="end"` 且 x 取值偏小，长标签会向**负 x 方向**溢出画布（实测 x0 = -42）。两种解法：
1. 左侧留足空间（`L ≥ 150`）并改用 `text-anchor="start"` + 固定 `x=18`
2. **把明细文字移到条形下方**另起一行，标签行只留短名称

自检脚本必须同时查 `x0 < -2`（左溢出）和 `x1 > viewBox宽`（右溢出），只查右溢出会漏。

交付时在对话中提供 HTML 文件的绝对路径，并提示用户用浏览器直接打开即可（Claude Code/WorkBuddy 类客户端通常会自动预览）。

## 常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 只用 MCP 大纲工具读文档 | 无 Heading 样式时返回空，误判文档无结构 | 直接用 zipfile 解析 document.xml |
| 只读开头就动手写报告 | 漏掉后半部分、漏掉复制残留问题 | 全文提取后 Read 通读 |
| 相信文档里写的数字 | 验收数量对不上却照抄，报告失去价值 | 逐项回原文点数，分口径统计 |
| 凭阅读印象回答"有没有规划" | 会说"应该有吧"，而点数结果是"0 次命中" | 用第 2.5 步关键词点数法，把命中行打出来人工判定 |
| 关键词命中就当作有效命中 | "基线"2 次命中实为「基线潜变量」术语，误判文档有基线描述 | 逐条看原文判定语义，无效命中要如实说明 |
| 只做正向统计不统计语气词 | 漏掉最有力的证据 | 反向扫「拟/将/有望」频次——实测 165 次「拟」直接证明全文是意向态 |
| 一次性 Write 整份 HTML | 39KB 处截断，JSON 解析失败 | 骨架 + 占位符 + 逐节 Edit |
| 手写 SVG 多列 x 坐标 | 框互相重叠、超出画布 | 脚本按 `(BW-gap*(n-1))/n` 算 |
| 生成 SVG 后不自检 | 渲染成一团才发现 | 必跑越界/重叠/文本溢出三项检查 |
| 文本溢出只查右边界 | 左侧 `text-anchor="end"` 标签向负 x 溢出（实测 x0=-42）漏检 | 同时查 `x0 < -2` 与 `x1 > viewBox宽` |
| 替换 SVG 块时只吃一个 `</div>` | 命中的是 `.cap` 的闭合，`.fig` 的闭合残留 → div 深度 -1（**已栽两次**）| 起点用 `<div class="fig"`，终点连续吃两个 `</div>` |
| 只查标签配对不查 div 深度 | 多一个 `</div>` 也能"配对" | 深度模拟：终值 0 且最小值 ≥0；再逐 section 查平衡差定位 |
| 靠标题文字匹配改章节编号 | 标题后带 `<span class="tag">` 时匹配失败，编号漏改 | 用正则按 sec-h 出现顺序统一重排，从后往前替换 |
